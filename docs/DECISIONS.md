# 技术选择与限制

## Docker 是唯一交付方式

项目不再把宿主机 Python 作为受支持路径。所有测试、训练、评估、推理和 API 操作都在容器中执行，避免宿主机 Python 版本、二进制扩展和虚拟环境残留造成不可复现问题。

开发训练镜像与发布镜像分离：开发镜像包含数据、测试和训练工具；发布镜像只包含 API 运行依赖与已经验证的模型。Kubernetes 只部署发布镜像。

## Python 版本固定为 3.13.15

`Dockerfile` 和 `Dockerfile.release` 都固定 Python 3.13.15 slim 基础镜像，默认通过 DaoCloud Docker Hub 代理拉取；`pyproject.toml` 要求 `>=3.13.15,<3.14`。这样容器内 Python 版本明确，不依赖宿主机版本。

基础镜像标签仍可能由镜像仓库重新指向不同摘要。正式发布时应记录基础镜像摘要、发布镜像摘要和构建时间；高要求环境应进一步按摘要固定 `FROM`。

## 为什么固定 CPU 版 PyTorch

当前交付目标是可在普通 Docker 主机复现的 CPU 流程。Dockerfile 先从阿里云 PyTorch CPU 镜像安装 `torch 2.8.0+cpu`，再从阿里云 PyPI 安装其余依赖，避免通用 Linux 包引入不需要的 CUDA 运行时和显著增加镜像体积。所有源都可以通过构建参数覆盖，直接依赖版本不随镜像切换。

需要 GPU 时必须另行评审基础镜像、NVIDIA Container Toolkit、驱动、CUDA 兼容性、Kubernetes RuntimeClass 和资源声明，不能把当前 CPU 镜像直接描述为 GPU 交付。

## 为什么选择 `hfl/rbt3`

`hfl/rbt3` 是较小的中文 RoBERTa 模型，CPU 训练和推理成本低于大型 BERT，适合演示完整流程。项目在 `configs/train.json` 固定提交 revision，避免上游仓库变化导致重复训练下载不同模型文件。

小模型和合成数据只用于工程闭环，不表示它是生产场景的最佳模型。生产选型仍需真实数据、延迟、容量、许可证和风险评估。

## 为什么使用合成数据

仓库中的中文电商评论由人工编写，不包含个人信息或客户数据。训练集、验证集和测试集固定并检查跨集合完全重复。

这些数据适合验证代码和容器链路，但不能支持商业准确率声明。真实落地需要业务代表性数据、统一标注规则、数据治理和独立验收集。

## 为什么关注投诉召回率

整体准确率可能掩盖少数类漏检，因此项目额外要求投诉召回率至少为 `0.70`。门槛只对当前合成测试集有效，不是生产服务等级承诺。

## 为什么使用宏平均 F1 选模

宏平均 F1 对四个类别等权，避免样本较多的类别掩盖较少类别。训练保存验证集宏平均 F1 最佳的模型，而不是无条件保存最后一轮。

## 为什么模型与 tokenizer 一起保存

训练把模型、tokenizer 和元数据一起写入 `artifacts/model/`。评估、CLI、Compose API 和发布镜像都读取这一目录，防止训练与服务使用不同的文本处理逻辑。

## 为什么模型不在开发镜像中

训练产物通过 Compose 绑定目录持久化，开发镜像可以重复使用。端到端验证通过后，`Dockerfile.release` 从已验证的本地开发镜像复制 Python 运行环境、移除测试工具，并把模型复制到发布镜像，避免重复下载大型依赖，也避免 API 容器启动时训练或下载基础模型。

## Kubernetes 边界

仓库提供 Deployment 和 ClusterIP Service 示例，不假设 Ingress、TLS、认证、镜像拉取凭据、网络策略、存储、GPU 或监控方案。部署步骤见 [KUBERNETES.md](KUBERNETES.md)。

本地 Docker 通过、发布镜像成功、镜像推送成功和 Kubernetes rollout 成功必须分别记录。没有获批集群和实时证据时，Kubernetes 状态必须为 `UNKNOWN`。

## 公开文档边界

公开文档从通用 `git clone` 开始，只使用仓库相对路径和明确占位符，不包含维护者用户名、盘符、工作区绝对路径、私有仓库或凭据。
