# 技术选择与原因

## 为什么选择 `hfl/rbt3`

`hfl/rbt3` 是三层中文 RoBERTa 预训练模型。相比更大的中文 BERT，它的下载、CPU 训练和本地推理成本更低，适合在普通本机上真实演示完整流程。

项目在 `configs/train.json` 中固定了具体模型提交版本。这样可以避免上游仓库变化造成重复训练时使用不同文件。当前固定版本还包含现代 Transformers 识别模型所需的 `model_type: bert` 配置。

选择小模型是为了让端到端流程可执行，不代表它一定是生产场景效果最好的模型。生产选型还要比较真实数据效果、推理延迟、硬件资源和许可证要求。

## 为什么使用合成数据

项目提交了人工编写的中文电商评论，避免使用个人信息或无法公开的业务数据。训练、验证、测试三份文件固定、类别平衡，并检查跨集合完全重复。

合成数据适合验证代码、训练、评估、推理和部署链路，但不能支持商业准确率声明。真实落地必须由业务和标注人员准备有代表性的真实数据，并制定一致的标签规则。

## 为什么重点检查投诉召回率

普通准确率只表示整体答对多少。如果真实投诉很少，即使模型漏掉全部投诉，整体准确率仍可能看起来不错。

因此项目额外设置投诉召回率门槛 0.70，要求至少识别出 70% 的真实投诉。本次测试达到 1.00，但测试集中只有 6 条投诉，所以该结果只证明验收机制可以工作，不是生产性能保证。

## 为什么使用宏平均 F1 选择最佳模型

宏平均 F1 分别计算每个类别的 F1，再给四类相同权重。它能避免数量多的类别掩盖数量少的类别。

当前数据恰好完全平衡，但保留宏平均 F1 作为选模指标，可以让流程更接近类别不平衡的真实业务场景。

## 为什么训练和服务共用保存后的 tokenizer

同一句文字必须在训练和推理时转换成相同 token。如果服务重新选择 tokenizer，即使模型文件没变，输入数字也可能不同，导致不可预测的结果。

因此训练会把模型和 tokenizer 一起保存到 `artifacts/model/`，命令行推理和 API 都只从该目录本地加载。

## 部署边界

API 可以作为本机进程运行，也提供 Docker 和 Kubernetes 打包文件。Kubernetes 清单中的镜像仓库地址有意保留为占位符。

当前已验证的是本机 FastAPI 部署。生产环境还需要镜像仓库、集群、入口与 TLS、监控告警、容量测试、权限控制、回滚策略和代表性生产数据。在这些证据完成前，不得声称通过生产或 Kubernetes 验收。
