# 从评论标注到在线预测：小林的 Docker 评论分类项目

> 这是一篇基于原博客改写的项目说明材料。它用“小林”的完整故事解释标注、数据集、开发、训练、评估、推理和上线，并把概念对应到本仓库已经验证的 Docker 流程。具体操作以 [README](../README.md) 为准。

## 一、业务问题是什么？

一家电商公司每天都会收到大量用户评论：

```text
“物流很快，产品也很好用。”
“软件更新以后经常崩溃。”
“感觉一般，没有特别满意。”
“客服一直不处理我的退款申请。”
```

运营人员希望自动识别：

- 正面评价，对应 `positive`；
- 负面评价，对应 `negative`；
- 中性评价，对应 `neutral`；
- 需要优先处理的投诉，对应 `complaint`。

算法工程师小林的工作，就是开发一个评论分类模型。以后每收到一条新评论，系统都能自动返回标签、置信度、四类得分和模型版本。

```text
输入：客服一直不处理退款
输出：complaint
```

这个仓库把完整流程实现为：

```text
准备合成评论
→ 固定标签
→ 划分并校验数据集
→ 加载固定版本的中文基础模型
→ CPU 微调
→ 独立测试集评估
→ 命令行推理
→ FastAPI 在线服务
→ 发布 Docker 镜像
→ 提供 Kubernetes 部署清单
```

本项目使用合成演示数据，不包含客户数据或个人信息，也不能代表真实业务准确率。

## 二、数据标注：先给模型准备“标准答案”

### 为什么需要标注？

模型一开始不知道什么是正面、负面、中性或投诉。小林必须先给它看带有标准答案的评论。

| 评论内容 | 项目标签 |
| --- | --- |
| 产品很好用，物流也很快 | `positive` |
| 软件更新后一直崩溃 | `negative` |
| 感觉一般 | `neutral` |
| 客服拒绝处理退款 | `complaint` |

这个给原始数据添加正确答案的过程，就叫数据标注。

### 标注时要注意什么？

小林需要先明确边界。例如：

```text
“商品很好，但客服太差了”算 negative 还是 complaint？
“一般般”算 neutral 还是 negative？
```

如果标注规则不一致，模型也会学得混乱。真实项目需要业务人员制定标签定义、处理冲突并抽查标注质量。本仓库为了演示工程流程，固定使用人工编写的四分类合成数据。

最直白地说：

> 标注就是给模型准备带答案的练习题。

---

## 三、整理数据集：把练习题分成三份

本项目严格划分三个互相隔离的数据集：

| 数据 | 数量 | 用途 |
| --- | ---: | --- |
| 训练集 | 500 | 让模型学习 |
| 验证集 | 120 | 训练过程中选择最佳模型 |
| 测试集 | 120 | 最后独立检查效果 |

可以类比为：

```text
训练集 = 平时练习题
验证集 = 模拟考试
测试集 = 最终考试
```

项目的数据校验会检查：

- 必需字段、空值和标签是否合法；
- 四个类别的样本数量是否符合预期；
- 单个数据集内是否存在重复评论；
- 训练集、验证集和测试集之间是否存在重复内容。

最直白地说：

> 数据集不是把文件放在一起就完成了，还要清洗、检查并严格隔离。

---

## 四、开发：先把方法和代码调通

小林需要实现一套程序：

```text
读取评论
→ 校验数据
→ 使用 tokenizer 处理文本
→ 加载基础模型
→ 训练并保存最佳模型
→ 独立评估
→ 推理
→ 提供 API
```

本项目不要求用户在宿主机安装 Python 或建立虚拟环境。代码、依赖、测试、训练和服务统一放在固定的 Docker 镜像中，减少环境差异造成的失败。

完整端到端容器依次执行：

```text
Ruff
→ Pytest
→ 三个数据集校验
→ 真实 CPU 训练
→ 独立测试集评估
→ 中文推理
```

只有命令退出码为 `0`，才表示整个链路通过。

最直白地说：

> 开发阶段先证明代码、数据、模型和服务能够在同一个可复现环境中闭环。

---

## 五、选择基础模型：不从零开始学习语言

小林没有从零训练语言模型，而是选择较小的中文 RoBERTa 模型 `hfl/rbt3`。

基础模型已经掌握一部分通用语言规律：

```text
“非常满意”通常表达积极态度
“一直崩溃”通常表达消极态度
“但是”前后可能出现语义转折
```

项目在 `configs/train.json` 中固定基础模型 revision：

```text
0412ffdc25bf738c556d523f8553bd69efe6405b
```

固定 revision 可以避免上游模型变化导致同一份代码在不同时间下载到不同内容。小林再使用四分类合成数据继续训练这个模型，这个过程叫微调。

```text
具备中文基础知识的模型
        +
带有四分类标签的评论
        ↓
本项目的评论分类模型
```

最直白地说：

> 基础模型像已经学过语文的学生，微调是让它继续学习当前项目的分类规则。

---

## 六、训练：让模型反复做题并改正错误

训练过程可以简化为：

```text
读取一批评论
→ 预测标签
→ 与标准答案比较
→ 计算误差
→ 调整模型参数
→ 继续下一批评论
```

本项目固定使用 PyTorch 2.8.0 CPU 轮子，默认训练 5 个 epoch，不要求 GPU 或 CUDA。训练过程根据验证集宏平均 F1 保存最佳模型，而不是简单保留最后一轮。

训练完成后，模型、同一个 tokenizer 和训练元数据写入 Docker 命名卷 `comment-classifier-artifacts`：

```text
/app/artifacts/model/
```

基础模型下载缓存写入另一个命名卷：

```text
/cache/huggingface/
```

因此，训练容器即使使用 `--rm` 自动删除，模型和缓存也仍然保留在 Docker 命名卷中。

最直白地说：

> 训练就是让模型大量做题并根据错误调整参数，最佳结果保存到持久化的 Docker 卷中。

---

## 七、评估：模型训练完，不代表模型真的好用

训练结束后，小林使用模型没有参与训练的测试集进行检查。

本项目最近一次本地完整验证结果为：

| 指标 | 结果 |
| --- | ---: |
| 测试准确率 | 0.958333 |
| 测试宏平均 F1 | 0.957685 |
| 投诉召回率 | 1.000 |
| 投诉召回率门槛 | 0.700，PASS |

只看准确率并不够。假设投诉数量很少，模型把投诉全部漏掉，整体准确率仍可能很高，但业务风险很大。因此，项目明确检查 `complaint` 的召回率。

评估完成后生成：

```text
/app/artifacts/reports/test_metrics.json
/app/artifacts/reports/test_predictions.csv
/app/artifacts/reports/test_report.md
```

这些数字只说明当前合成测试集和当前容器链路通过，不能直接外推为生产效果。

最直白地说：

> 训练是学习，评估是独立考试；模型能运行，不等于模型适合真实业务。

---

## 八、推理：让训练好的模型回答新问题

推理是使用已经训练好的模型处理新的评论：

```text
新评论：客服一直不处理退款
        ↓
训练好的评论分类模型
        ↓
complaint + 置信度 + 四类得分
```

训练和推理的区别：

| 阶段 | 目的 | 输入 | 输出 |
| --- | --- | --- | --- |
| 训练 | 让模型学习 | 大量评论和正确标签 | 模型、tokenizer 和元数据 |
| 推理 | 使用模型 | 一条新评论 | 标签、置信度、四类得分和模型版本 |

推理容器以只读方式挂载模型卷，避免一次查询意外修改训练产物。

最直白地说：

> 训练是让模型学习，推理是让学会后的模型正式答题。

---

## 九、上线：把模型变成其他系统能调用的服务

训练完成后，小林得到的是模型文件。业务系统还需要一个可以长期接收请求的接口。

本项目使用 FastAPI 提供两个主要接口：

```text
GET  /health
POST /predict
```

预测请求示例：

```http
POST /predict
Content-Type: application/json

{
  "text": "物流很快，商品也很好用"
}
```

返回内容包括：

```json
{
  "label": "positive",
  "confidence": 0.99,
  "scores": {
    "positive": 0.99,
    "negative": 0.00,
    "neutral": 0.00,
    "complaint": 0.00
  },
  "model_version": "示例版本"
}
```

开发 API 从模型卷读取产物；发布镜像则把已验证的模型和 tokenizer 一起打入镜像，不再依赖训练卷。远端发布镜像为：

```text
songleo/comment-classification-e2e:0.1.0
```

最直白地说：

> 上线就是把模型包装成健康可检查、长期可调用的接口。

## 十、容器交付和 Kubernetes 边界

本项目的唯一交付方式是标准 Docker CLI。用户可以选择：

```text
取得源码
→ 本地构建开发镜像
→ 完整训练和验证
→ 导出模型
→ 构建发布镜像
```

也可以跳过训练，直接拉取已经发布的镜像验证 API：

```text
docker pull songleo/comment-classification-e2e:0.1.0
```

仓库还提供 Kubernetes Deployment 和 ClusterIP Service 清单，并固定到已经验证的发布镜像摘要。本地已经使用 Docker 容器完成 schema 校验，但没有获批集群、服务端 dry-run、rollout 或集群接口证据。

因此，当前状态必须区分：

| 阶段 | 状态 |
| --- | --- |
| 本地 Docker 端到端 | 已验证 |
| 发布镜像独立运行 | 已验证 |
| Docker Hub 拉取运行 | 已验证 |
| Kubernetes 清单 schema | 已验证 |
| Kubernetes 实际集群部署 | `UNKNOWN` |

最直白地说：

> 有部署清单不等于已经在真实集群上线，必须用实际集群证据单独验收。

## 十一、上线不是结束：还要监控和持续改进

真实用户表达会变化，新产品也会带来新的问题。生产项目需要持续观察：

- 每天处理多少条评论；
- 接口响应是否稳定；
- 哪些评论经常出现低置信度；
- 哪些结果被业务人员纠正；
- 新表达是否经常判断错误；
- 新版本是否比旧版本稳定。

运营人员纠正的错误案例可以形成新的闭环：

```text
线上错误案例
→ 人工重新标注
→ 数据治理和隐私检查
→ 加入新数据集
→ 再次训练和独立评估
→ 构建新镜像
→ 灰度发布并监控
```

本仓库没有真实线上数据、生产监控或自动反馈闭环，这些内容属于后续真实业务建设范围。

最直白地说：

> 模型不是开发一次就永远不变，而是要根据真实、合规的业务反馈持续更新。

## 十二、小林最终交付了什么？

小林最终交付的不只是一个模型文件，而是一套可复现材料：

```text
固定的四分类标签
经过校验的三份合成数据集
固定 revision 的中文基础模型配置
数据校验、训练、评估和推理代码
训练后的模型与同一个 tokenizer
JSON、CSV 和 Markdown 评估报告
FastAPI 在线接口
开发镜像与独立发布镜像
Docker Hub 发布镜像
Kubernetes 部署清单和边界说明
完整 Docker 文档与验证记录
```

模型默认保存在 Docker 命名卷中。只有构建发布镜像时，才通过临时容器和 `docker cp` 把已验证模型导出到项目的构建目录。

## 十三、用一张图回顾完整项目

```text
业务提出问题
“能否自动识别评论情绪和投诉？”
        ↓
固定 positive、negative、neutral、complaint 四个标签
        ↓
准备并校验三份合成数据集
        ↓
构建固定 Python 和 PyTorch 版本的开发镜像
        ↓
微调固定 revision 的 hfl/rbt3
        ↓
将最佳模型和 tokenizer 保存到 Docker 命名卷
        ↓
使用独立测试集评估
        ↓
对新评论进行推理
        ↓
启动并验证 FastAPI
        ↓
把模型打入发布镜像
        ↓
拉取远端镜像复测
        ↓
校验 Kubernetes 清单
        ↓
等待获批集群进行独立部署验收
```

核心概念可以这样记：

```text
数据标注 = 给评论添加标准答案
数据集 = 模型学习、选择和考试使用的材料
开发镜像 = 固定代码、Python 和依赖的训练环境
基础模型 = 已经掌握通用中文知识的模型
微调 = 使用项目数据继续训练基础模型
训练 = 让模型做题、计算错误并调整参数
评估 = 使用未见过的数据独立检查效果
推理 = 使用训练好的模型处理新评论
命名卷 = 在临时容器删除后继续保存模型和报告
发布镜像 = 已经包含模型与 tokenizer 的独立服务镜像
在线推理服务 = 持续接收评论并返回预测结果的 API
```

小林完成的事情，可以用一句话概括：

> 她把四分类评论数据做成可校验的数据集，在固定的 Docker 环境中微调并评估中文基础模型，把最佳模型与 tokenizer 保存并打入发布镜像，最后提供可调用的 API 和边界清晰的 Kubernetes 部署材料。
