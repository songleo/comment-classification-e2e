## 1. 先看完整流程

可以把整个项目理解为“学生学习并参加考试”：

```text
准备带答案的评论
        ↓
检查数据是否合格
        ↓
训练集：学生平时练习
        ↓
验证集：训练过程中做模拟考试，选择表现最好的模型
        ↓
测试集：模型确定后做最终考试
        ↓
推理：让模型回答一条从未见过的新评论
        ↓
API 服务：把模型变成其他程序能长期调用的网络接口
```

本项目不是只打印一组演示结果。训练命令会真正加载中文预训练模型、计算错误、反向传播、修改模型参数，并保存修改后的模型文件。

## 2. 模型要解决什么问题

输入是一条中文电商评论，输出是下面四类之一：

| 标签 | 直白解释 | 例子 |
| --- | --- | --- |
| `positive` | 用户明确满意 | 物流很快，商品也很好用 |
| `negative` | 用户不满意，但没有要求人工介入 | 软件更新后经常崩溃 |
| `neutral` | 只是在陈述事实，没有明显褒贬 | 订单显示明天下午送达 |
| `complaint` | 用户要求退款、申诉、调查或升级处理 | 客服一直不处理退款申请 |

`complaint` 和 `negative` 最容易混淆。这个项目采用的规则是：如果用户明确要求平台、客服或负责人采取行动，优先标成 `complaint`。

## 3. 为什么要准备三份数据

当前数据量为：

| 数据 | 数量 | 每类数量 | 用途 |
| --- | ---: | ---: | --- |
| 训练集 `train.csv` | 100 | 25 | 真正修改模型参数 |
| 验证集 `validation.csv` | 24 | 6 | 每轮训练后检查效果并选择最佳模型 |
| 测试集 `test.csv` | 24 | 6 | 训练完成后做一次独立最终检查 |

三份数据不能互相重复。如果同一句评论同时出现在训练集和测试集里，就像把考试原题提前给学生，测试分数会虚高。

数据校验程序会检查：

- 三份数据是否为空；
- 是否只出现四个规定标签；
- 每份数据是否都包含四个类别；
- 评论内容是否为空；
- 去掉空格并转成小写后，是否跨数据集出现完全相同的评论。

目前的数据是人工编写的合成数据，适合验证完整流程，但数量远小于真实业务数据。因此它不能证明模型已经达到生产准确率。

## 4. 基础模型、微调和分类头是什么

### 4.1 基础模型

项目使用 `hfl/rbt3`。它已经学习过大量中文文本，知道常见中文词语和上下文关系，但它一开始不知道本项目的四个业务标签。

第一次执行训练时，程序会自动从 Hugging Face 下载 `configs/train.json` 中固定版本的
tokenizer 和基础模型，并保存到 Hugging Face 本地缓存；不需要手工把模型文件复制到项目中。
缓存完整后，后续训练可以复用它。微调完成后，训练程序会把模型和同一套 tokenizer 保存到
`artifacts/model/`，预测命令和 API 只读取这个本地产物，不会再次下载基础模型。

可以把它理解为“已经学过中文，但还没有学过公司分类规则的学生”。

### 4.2 分类头

加载基础模型时，程序会新建一个四分类输出层，也叫分类头。它负责把模型理解到的文本特征转换成四个分数。

第一次训练时看到下面的提示是正常的：

```text
classifier.bias 和 classifier.weight 是新初始化的
```

它表示基础模型没有原生的四分类答案层，所以项目新建了这一层，接下来必须使用业务数据训练它。

### 4.3 微调

本项目不是只训练最后一层，而是把整个模型参数交给 AdamW 优化器。每批数据都会执行：

```text
把文字转换成 token 数字
→ 模型给出四类分数
→ 与正确标签比较并计算 loss
→ 反向传播计算每个参数应该怎样调整
→ 优化器更新模型参数
```

这就是实际的 Transformer 微调。

## 5. 训练配置逐项解释

配置文件是 `configs/train.json`。

### `base_model: "hfl/rbt3"`

指定从哪个中文预训练模型开始学习。换成其他模型后，下载大小、训练速度、内存占用和效果都可能变化。

### `model_revision: "0412ffdc..."`

固定基础模型仓库的具体提交版本。这样以后重复训练时，不会因为模型仓库更新而悄悄换成不同文件。

### `max_length: 96`

每条评论最多处理 96 个 token。token 是 tokenizer 切分后的数字单元，不一定等于 96 个汉字。

- 评论不足 96 个 token：补齐到固定长度，补齐位置通过 `attention_mask` 告诉模型不要当成正文。
- 评论超过 96 个 token：后面的内容会被截断。
- 设得太小：重要的后半句可能被截掉，例如“商品不错，但是客服拒绝退款”中的转折和投诉信息。
- 设得太大：训练更慢、占用更多内存，而短评论会产生更多无效补齐。

当前演示评论都较短，所以 96 是偏保守且足够的长度。真实业务应统计评论长度分布后再决定。

### `batch_size: 8`

一次把 8 条评论交给模型计算，然后更新一次参数。

- 训练集有 500 条，因此每个 epoch 大约有 63 个 batch。
- 设得更大：通常运行效率更高，但需要更多内存。
- 设得更小：内存需求更低，但梯度波动更大，训练步骤更多。

这个值主要受显存或内存限制影响，不是越大越好。

### `epochs: 5`

让模型最多完整学习训练集 5 遍。一遍称为一个 epoch。

- 太少：模型可能还没有学会，称为欠拟合。
- 太多：模型可能只记住训练数据，对新数据反而变差，称为过拟合。

程序同时配置了早停，所以 5 是上限，不保证每次都会运行满 5 轮。

### `learning_rate: 0.00003`

写成科学计数法是 `3e-5`。它控制每次更新模型参数的步幅。

- 太大：模型可能跨过正确方向，loss 剧烈波动甚至训练失败。
- 太小：学习非常慢，在有限 epoch 内没有明显进步。

预训练 Transformer 微调通常使用较小学习率，因为基础模型已经学到了中文知识，不希望一次修改得过猛。

### `weight_decay: 0.01`

权重衰减会轻微限制参数变得过大，是一种正则化手段，目的是降低模型死记训练数据的风险。

- `0` 表示不使用这项约束。
- 值太大可能阻碍模型学习。
- 当前 `0.01` 是温和约束，但不能替代更多真实数据。

### `seed: 42`

固定 Python 和 PyTorch 的随机种子，让训练集打乱顺序和参数更新尽可能可复现。

同一个 seed 有助于比较两组配置，但不代表在所有硬件上都能得到逐位完全相同的结果。正式实验通常会使用多个 seed 重复训练，观察结果是否稳定。

### `early_stopping_patience: 2`

每个 epoch 后，程序检查验证集宏平均 F1：

- 如果比历史最佳值更高，保存这一轮为当前最佳模型，并把等待计数清零。
- 如果没有严格变高，等待计数加一。
- 连续 2 轮没有变好，就提前停止。

注意：早停看的是验证集宏平均 F1，不是验证集 loss。

### `min_complaint_recall: 0.70`

这是最终评估门槛，意思是测试集中的真实投诉至少应识别出 70%。

它不参与 loss 计算，也不会直接指导训练。评估程序只在训练完成后比较：

```text
实际投诉召回率 >= 0.70 → PASS
实际投诉召回率 < 0.70  → FAIL
```

本次测试有 30 条合成投诉，因此门槛只能用于演示验收机制，不能作为生产发布标准。

## 6. 代码中还有哪些没有写进配置文件的参数

| 项目 | 当前值或行为 | 直白解释 |
| --- | --- | --- |
| 优化器 | AdamW | 根据梯度更新模型参数，并应用权重衰减 |
| 梯度裁剪 | 最大范数 1.0 | 防止某次梯度异常大导致训练不稳定 |
| 训练集顺序 | 每轮打乱 | 避免模型一直按完全相同顺序看数据 |
| 验证集顺序 | 不打乱 | 评估不需要随机顺序 |
| padding | 补到 `max_length` | 让同一 batch 中张量长度一致 |
| 设备选择 | 自动检测：有 CUDA 用 NVIDIA GPU，否则用 CPU | 当前参考环境是 `torch 2.8.0+cpu`，本次实测使用 CPU；换成兼容的 CUDA 版 PyTorch 后通常不需要改代码 |
| 最佳模型选择 | 验证集宏平均 F1 最高 | 最终保存的不是简单的“最后一轮”，而是最佳轮次 |
| 输出概率 | softmax | 把四个原始分数转换为总和约为 1 的相对概率 |

## 7. 怎样读懂本次训练过程

本次实际训练记录如下：

| Epoch | 训练 loss | 训练宏平均 F1 | 验证 loss | 验证宏平均 F1 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 0.8540 | 0.6759 | 0.2669 | 0.9585 |
| 2 | 0.1909 | 0.9459 | 0.1015 | 0.9591 |
| 3 | 0.0447 | 0.9900 | 0.0695 | 0.9833 |
| 4 | 0.0076 | 0.9980 | 0.0161 | 1.0000 |
| 5 | 0.0018 | 1.0000 | 0.0307 | 0.9835 |

### loss 是什么

loss 是模型“错得有多严重”的数学分数，越低通常越好，但它不是错误条数，也不是百分比。

本次训练 loss 从 0.8540 降到 0.0018。验证 loss 在第 4 轮降到最低的 0.0161，第 5 轮回升到 0.0307；程序因此保存第 4 轮的最佳模型。

### 为什么第 5 轮的 F1 下降，却保存第 4 轮

第 4 轮验证宏平均 F1 达到 1.0000，是新的最佳轮次。第 5 轮回退到 0.9835，但程序不会用较差的最后一轮覆盖最佳权重；训练达到配置的 5 个 epochs 后，重新加载并保存第 4 轮的权重。

### 训练 F1 等于 1.0 是否代表模型完美

不代表。它只表示模型在当前 500 条合成训练数据上全部判断正确。合成小数据很容易被模型记住。真正应该关注的是未参与参数更新的验证集和测试集，以及更大规模的真实业务数据。

## 8. 怎样读懂本次测试结果

测试集共 120 条，模型答对 115 条、答错 5 条：

```text
准确率 = 115 ÷ 120 = 0.95833 = 95.8%
```

测试集扩充后，每错一条会让整体准确率变化约 0.83 个百分点，比原来更稳定，但规模仍然不足以代表真实业务分布。

### 每类结果

| 类别 | Precision 精确率 | Recall 召回率 | F1 | Support 实际样本数 | 直白解释 |
| --- | ---: | ---: | ---: | ---: | --- |
| positive | 1.000 | 0.867 | 0.929 | 30 | 预测为正面的都对，但 30 条真实正面漏掉了 4 条 |
| negative | 0.935 | 0.967 | 0.951 | 30 | 30 条真实负面找回 29 条，另有 2 条正面被误判为负面 |
| neutral | 0.938 | 1.000 | 0.968 | 30 | 30 条真实中性全部找回，另接收了 2 条错误预测 |
| complaint | 0.968 | 1.000 | 0.984 | 30 | 30 条真实投诉全部找回，另有 1 条正面被误判为投诉 |

### Precision、Recall 和 F1 的直白解释

- Precision：模型说“这是某一类”时，有多少是真的。例如负面精确率 `29/31=0.935`，因为模型一共说了 31 次负面，其中 29 次正确。
- Recall：真实属于某一类的样本中，模型找回了多少。例如正面召回率 `26/30=0.867`，因为 30 条真实正面找回 26 条。
- F1：综合 Precision 和 Recall。只有两者都较高，F1 才会较高。
- Support：测试集中这个类别实际有多少条，不是模型预测了多少条。

### Macro F1 和 Weighted F1

- 宏平均 F1：先分别计算四个类别的 F1，再做简单平均。每个类别权重相同，适合防止多数类别掩盖少数类别问题。
- 加权 F1：按每类实际样本数加权。本项目四类各 30 条，数量完全相同，所以宏平均和加权结果相同，都是约 0.958。

### 投诉召回率为什么是 100%

测试集中有 30 条合成投诉，模型全部识别出来：

```text
投诉召回率 = 30 ÷ 30 = 1.0
```

因此超过配置中的 0.70 门槛，验收结果为 PASS。但这里只测试了 30 条合成投诉，不能推断真实环境中成千上万种投诉表达也能达到 100%。

## 9. 混淆矩阵怎样看

程序输出的类别顺序固定为：

```text
positive, negative, neutral, complaint
```

本次矩阵为：

| 真实类别 \ 预测类别 | positive | negative | neutral | complaint |
| --- | ---: | ---: | ---: | ---: |
| positive | 26 | 2 | 1 | 1 |
| negative | 0 | 29 | 1 | 0 |
| neutral | 0 | 0 | 30 | 0 |
| complaint | 0 | 0 | 0 | 30 |

按行读取：第一行表示 30 条真实正面中，26 条预测为正面，2 条预测为负面，还各有 1 条预测为中性和投诉。对角线上的数字是正确数量，非对角线数字是误判数量。

五条误判样本是：

```text
平板电脑手写延迟很低，记笔记非常顺手：positive -> negative
防水背包遇到大雨也没有打湿里面的电脑：positive -> negative
客服清楚说明了保修到期日期，还教了保养方法：positive -> complaint
税号修正后电子发票立即重新开好了：positive -> neutral
保修到期提醒比实际日期晚了两个月：negative -> neutral
```

这些错误显示模型会过度关注“延迟”“打湿”“客服”“发票”和“保修”等局部词语。错误分析不能只看总分，还要阅读具体误判文本。

## 10. 置信度为什么高也可能答错

推理时，模型会输出四个分数，softmax 把它们转换成总和约为 1 的相对概率。最高分对应最终标签，最高分就是 `confidence`。

例如：

```json
{
  "label": "complaint",
  "confidence": 0.998949,
  "scores": {
    "positive": 0.000462,
    "negative": 0.000162,
    "neutral": 0.000427,
    "complaint": 0.998949
  }
}
```

`0.998949` 表示模型在自己的四个选择中强烈倾向于投诉，不表示现实世界中有经过统计证明的 99.8949% 正确概率。

小数据微调后的模型可能“很自信地答错”。如果业务需要依据置信度自动处置，还要使用更大的独立数据做概率校准，并设计低置信度转人工规则。

## 11. 模型版本是什么

`model_version` 是模型保存时生成的 UTC 时间戳。例如：

```text
20260828T123504Z
```

它表示 2026-08-28 12:35:04 UTC，对应北京时间 2026-08-28 20:35:04。

它用于区分不同训练产物，不代表模型效果高低。每次重新训练并保存，版本时间都会变化。

## 12. 推理和训练有什么区别

训练：

- 输入评论和正确标签；
- 计算 loss；
- 反向传播；
- 修改模型参数；
- 需要更多时间和内存。

推理：

- 只输入新评论；
- 不需要正确标签；
- 不计算梯度，也不修改参数；
- 返回标签、置信度、各类分数和模型版本。

推理程序强制从 `artifacts/model/` 本地加载模型和 tokenizer，确保服务使用的就是训练保存的产物。

## 13. API 上线做了什么

模型文件本身不能接收 HTTP 请求。FastAPI 把推理过程包装成两个接口：

- `GET /health`：确认模型可以加载，并返回模型版本。
- `POST /predict`：接收一条评论并返回分类结果。

请求正文：

```json
{"text": "客服一直不处理退款"}
```

返回正文包含：

- `label`：最终选择的类别；
- `confidence`：最终类别的 softmax 分数；
- `scores`：全部四类分数；
- `model_version`：当前服务加载的模型版本。

API 对输入文本的限制是 1 到 1000 个字符。模型内部仍会按照 `max_length=96` 个 token 截断。

## 14. 初学者调试时先看什么

### 训练 loss 基本不下降

优先检查：标签是否正确、学习率是否过小或过大、分类数量是否匹配、数据是否真的进入训练程序。

### 训练 F1 上升，验证 F1 下降

通常是过拟合信号。优先增加真实多样数据、检查重复样本、减少 epoch，不能只追求训练分数。

### 验证很好，测试明显变差

可能反复根据验证集调参，已经间接“适应”验证集；也可能测试集分布不同。测试集应保留到最终检查，不能频繁用于调参。

### 高置信度误判

不要直接把置信度当成正确概率。阅读误判样本，检查否定、转折、行业词语和标签规则，并补充有代表性的训练数据。

### 提示找不到训练模型

确认存在：

```text
artifacts/model/config.json
```

如果不存在，先执行训练命令。

### 8000 端口被占用

说明已有服务正在使用该端口。停止旧服务，或者启动时改用 `--port 8001`。

### PowerShell 调用接口时中文被错误分类

Windows PowerShell 5.1 发送不带字符集声明的中文 JSON 字符串时，服务可能收到错误编码
的内容。请求中文文本时应显式使用：

```powershell
-ContentType 'application/json; charset=utf-8'
```

如果同一句中文在命令行推理中结果正确、通过 `Invoke-RestMethod` 调用却明显异常，应先
检查这一项，而不是立即重新训练模型。

## 15. 当前项目已经证明了什么

已经用实际执行证据证明：

- 三份数据能够读取并通过隔离校验；
- 中文基础模型能够在 CPU 上完成真实微调；
- 最佳验证模型能够保存并重新加载；
- 独立测试集能够生成逐条预测和分类指标；
- 命令行推理和 HTTP API 能使用同一个模型产物；
- 本地服务能够健康检查并处理真实请求。

没有证明：

- 对真实电商海量评论仍有 95.8% 准确率；
- 投诉召回率在生产环境仍为 100%；
- 当前置信度已经完成概率校准；
- 当前合成数据已经覆盖方言、错别字、反讽、长文本和新业务表达；
- Docker、Kubernetes 或公网生产环境已经验收。

最合理的下一步不是盲目增加 epoch，而是收集更多经过人工复核的真实业务评论，完善标注规则，再重新划分数据并重复同一套流程。
